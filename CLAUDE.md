# Contexte projet — Bot Famille (bot Discord RP FiveM générique)

Notes de conventions et de pièges pour un agent Claude Code reprenant ce projet (ou un projet similaire : bot Discord + FiveM RP + PostgreSQL/Prisma + TypeScript).

## Stack & déploiement

- TypeScript (compilé en CommonJS via `tsc`, pas d'ESM), discord.js v14, Prisma/PostgreSQL, `node-cron`, `dotenv`. API REST optionnelle (`src/api/`) : Express, `cors`, `jsonwebtoken` — voir plus bas.
- `npm run dev` (tsx, à chaud) en développement ; `npm run build && npm start` en production.
- Deux modes de déploiement supportés (pas de PM2) — **Docker est le mode recommandé, présenté en premier dans le README** ; systemd reste une alternative pleinement supportée, à maintenir au même niveau (décision explicite de l'utilisateur) :
  - **systemd** : après un déploiement : `git pull && npm install && npx prisma migrate deploy && npm run build && sudo systemctl restart roxwood-network-famille.service`
    - Logs : `sudo journalctl -u roxwood-network-famille.service -n 50 --no-pager`
    - Toujours `npx tsc --noEmit` avant de redémarrer, pour attraper les erreurs de type/syntaxe sans faire planter le service.
  - **Docker** (`Dockerfile` + `docker-compose.yml`, à la racine) : conteneurise le bot ET PostgreSQL (service `db`, volume nommé). `docker-entrypoint.sh` lance `prisma migrate deploy` avant de démarrer le bot à chaque `docker compose up`/redémarrage de conteneur — pas besoin de l'appeler à la main comme en systemd. Mise à jour : `git pull && docker compose up -d --build`.
    - L'image (`node:20-alpine`) a besoin d'`apk add openssl` : sans ça, le moteur Prisma échoue au démarrage avec une erreur de parsing qui masque le vrai problème.
    - Build observé cassé (`invalid file request`) avec BuildKit sur Windows + OneDrive sur ce poste précisément — `DOCKER_BUILDKIT=0` en solution de contournement si ça se reproduit.
- Le langage de toutes les interactions Discord (embeds, messages, boutons) est le **français**.
- **Toujours répondre en français à l'utilisateur**, dans toutes les réponses de l'agent (texte, résumés, questions), quelle que soit la langue du message reçu — décision explicite de l'utilisateur.

## Le modèle de configuration — piège n°1 : orthographe des items FiveM

Toute la configuration métier (items, activités, quotas, salons, rôles…) vit en base et se pilote via `/config` (voir `src/modules/config.ts`), **jamais** dans un fichier de code. `config-store.ts` maintient un cache en mémoire rechargé par `configStore.reload()` à chaque écriture `/config` — toujours utiliser `configStore.get()` (jamais mettre son résultat en cache dans une variable de module chargée une seule fois, sinon les changements de config ne seraient visibles qu'après redémarrage).

Toute écriture de config passe par `configStore.mutate(() => db.xxx(...))` plutôt que par `db.xxx(...)` suivi d'un `configStore.reload()` manuel — `mutate()` recharge systématiquement après coup, donc impossible d'oublier le reload en ajoutant une nouvelle sous-commande `/config`.

`/config item add <nom>` doit correspondre **exactement** (accents, casse) à ce qu'écrit le bot de jeu FiveM dans les logs de coffre. Tout item absent de la liste est **silencieusement ignoré** — pas d'erreur, pas de warning, juste des mouvements de stock qui n'apparaissent jamais. C'est la source de bug la plus fréquente sur ce type de projet.

**Ne jamais deviner/renommer un nom d'item sans vérification.** Avant tout ajout, aller lire les vrais logs récents du salon coffre concerné pour confirmer l'orthographe exacte utilisée en jeu (voir « Scripts d'investigation » ci-dessous).

Comme `MUNITIONS_STOCK_GROUP` pour les munitions, `CONFIRME_VENTE_ITEM` (`modules/ventes.ts`, "Argent Sale") est un nom d'item fixé en dur plutôt qu'un flag `/config item add` : un seul item confirme les ventes de drogue en attente en pratique, pas besoin d'exposer une option que personne d'autre ne touchera jamais. `/config item list` affiche quand même un badge 🪙 dessus (comparaison par nom, pas un champ en base) pour rester visible. Contrairement à `MUNITIONS_STOCK_GROUP` (un `groupe` choisi librement par l'admin), `CONFIRME_VENTE_ITEM` EST un nom d'item exact comparé aux dépôts réels — le piège n°1 s'applique donc pleinement ici : ne jamais changer cette constante sans vérification explicite avec l'utilisateur.

`src/default-items.ts` pré-remplit une liste d'items connus (nom vérifié avec l'utilisateur, pas deviné — le fichier fait foi pour la liste exacte) s'ils sont absents — les items génériques ("Munition de pistolet" et "Boîte mun. pistolet" à `stockMultiplier: 24`, groupe `MUNITIONS_STOCK_GROUP` ; "Munition de SMG" via `MUNITIONS_SMG_ITEM`, sans groupe ; `CONFIRME_VENTE_ITEM` lui-même, "Argent Sale" — c'est `ventes.ts` qui lui donne son rôle, pas un flag posé à la création ; "Argent", simple item de stock distinct de l'Argent Sale), le butin et les outils de casse, les drogues vendables, et les items/matériaux des labos du registre fixe (Salvia volontairement SANS `labo_lie`, donc toujours vendable ; produit de `labo_branche_cannabis`, matériaux de `labo_salvia`/`labo_sporex`/`labo_heroine` — voir `laboLieRole` plus bas). Déclenché à la fois au démarrage du bot (`index.ts`) et à chaque usage de `/config` (`modules/config.ts`) — pas seulement au tout premier démarrage du process, pour qu'un bot déjà en cours d'exécution en profite aussi (idempotent, sans double-appel problématique). Jamais d'écrasement d'un item déjà configuré (comparaison par nom insensible à la casse avant insertion, comme partout pour un item) — reste un point de départ éditable via `/config item`, pas un registre fixe comme `ACTIVITY_TYPES_FIXED`. Ajouter une entrée ici sans la même vérification explicite auprès de l'utilisateur reproduirait exactement le piège n°1.

## Portée de la généralisation (décisions de conception)

- **Configurables via `/config`** : items, objectifs de quota, taux et paliers de paie, points de classement, salons, rôles — tout ce qui peut réellement changer/être renégocié après le déploiement du bot.
- **Restent fixes dans le code, volontairement pas de `/config` dédié** — valeurs jugées suffisamment stables une fois le bot déployé pour une organisation donnée :
  - Registre des activités déclarables (`ACTIVITY_TYPES_FIXED` dans `src/config-store.ts`) : ATM, Cambu, Supérette, Go Fast, Armurerie, Fleeca, Bijouterie, Pinebank, Human Labs (organes), Vente, Récolte, Labo Héroïne, Labo Spore X, Labo Mexicana, Labo Cannabis, Labo Cocaïne, Labo Salvia, Labo Branche De Cannabis — libellé, cooldown, limite de braquage, mode labo, catégorie de quota. Repris tel quel du bot d'origine (sauf Human Labs + les labos ajoutés pour le système de type d'organisation ci-dessous, dont Salvia/Branche De Cannabis pour le tier Indépendant). Seuls les salons `labo_*` restent configurables via `/config channel` (des IDs propres à chaque serveur Discord, pas des valeurs métier).
  - Types de taxe (`sporex`/`heroine`/`vente`/`fertilisant`/`cannabis`/`mexicana`/`cocaine`/`salvia` + les taxes de zone) : chacun a des champs de modal hétérogènes (zone a téléphone + sélection préalable de zone, les autres non) — les rendre dynamiques demanderait un moteur de formulaire générique. Seuls salon/rôle/échéances sont configurables pour les taxes. Les taxes de zone stockent le nom de la zone directement dans le champ `type` (voir `ZONES_BY_TIER`/`ZONE_BY_KEY` dans `src/modules/taxes.ts`), pas de colonne séparée. Types de taxe et zones dépendent aussi du tier (`TAXES_FIXES_BY_TIER`/`ZONES_BY_TIER`, même principe que `LABO_TIERS`) mais **indépendamment** de celui-ci : Gang a `cannabis`, Organisation a `mexicana`+`cocaine` (alors que le labo Mexicana est accessible à Gang ET Organisation), Petite Frappe a `salvia` (alors que le labo Salvia est accessible au tier Indépendant), et Gang/Organisation partagent les mêmes 18 zones (pas de découpage exclusif comme pour les labos) — ne pas supposer que le barème d'une taxe se déduit de `LABO_TIERS`, vérifier `TAXES_FIXES_BY_TIER`/`ZONES_BY_TIER` directement.
  - Types d'armes (`ARME_TYPES` en tête de `src/modules/armurerie.ts`) — 36 modèles en 4 catégories, déjà remplis pour ce serveur.
  - Plafonds indicatifs de munitions et amende de fourrière (`src/modules/armurerie.ts`, `src/modules/garages.ts`) — purement informatifs, aucune facturation automatique nulle part dans le bot. Le stock réel de munitions affiché dans l'embed armurerie vient d'un item `/config item add` normal, associé via son `groupe` à la constante fixe `MUNITIONS_STOCK_GROUP` (`'Munition de pistolet'`, câblée dans `armurerie.ts`) — volontairement un libellé de groupe choisi par l'admin, pas un nom d'item exact (contrairement au piège n°1), pour ne pas dépendre de l'orthographe précise des logs FiveM. Un item d'un `STOCK_GROUP` peut valoir plusieurs unités de base (ex. "Boîte mun. pistolet" = 24 "Munition de pistolet") : `Item.stockMultiplier` (`/config item add ... multiplicateur:`, défaut 1) pondère chaque item avant de sommer un groupe, via `armurerie.weightedStockSum` réutilisée telle quelle par `stocks.buildStockEmbed` — une seule logique de pondération, pas deux calculs divergents entre l'armurerie et le Stock Général. Volontairement un champ par item (comme `stockGroup`/`vente`) plutôt qu'une constante `nom → multiplicateur` codée en dur : un item déjà résolu porte directement son propre multiplicateur, sans second matching par nom qui pourrait diverger (piège n°1 appliqué à un facteur plutôt qu'à une présence/absence).
- **Le rappel de quota du dimanche** (`quotas.checkQuotaReminder`) reste spécifique à la catégorie de quota `vente` (couplé au cycle de vente de drogue) — pas de règle non-arbitraire pour généraliser à "n'importe quelle catégorie".
- **La paie** (`/config salaire`) est un taux ($ par unité) par catégorie de quota, indépendant des objectifs (`/config quota`) — une catégorie peut avoir l'un, l'autre, les deux, ou aucun. Une catégorie sans taux ni palier ne génère aucune paie. "Ma Paie" (rang compris) vient de `quotas.getSalaryRanking()` (live, `Stat`), la paie hebdomadaire publiée de `quotas.getAllUserPayForRange()` sur la période close (`Transaction`, voir Robustesse) — même calcul `computeSalaireTotal` dans les deux cas. Un taux ou palier par item est enregistré sous le nom configuré mais comparé en minuscules aux ventes (`quotas.lowerKeys`), comme partout pour un item.
  - **Le classement de groupe n'est PAS la paie** : bouton "Classement Groupe", trié par points de classement (`/config classement`, `quotas.getClassementRanking`), par catégorie et optionnellement par activité pour "actions". Un membre peut être premier ici sans être payé. Non historisé non plus (même piège que `/config salaire`, voir API).
  - **`/config palier`** (uniquement pour la catégorie "vente", décision explicite de l'utilisateur — pas généralisé aux autres catégories) : barème progressif par tranche de quantité, alternative au taux plat de `/config salaire`. Palier PROGRESSIF (comme un barème d'impôt) : chaque tranche `[borne précédente, upTo]` est payée à son propre taux, jamais un seuil qui repaierait toute la quantité au taux de la dernière tranche atteinte — voir `quotas.computeTierPay`. `item` optionnel cible une drogue précise (coexiste avec `ITEM_SALARY_RATES`, taux plat par item) ; priorité de résolution PAR ITEM : palier propre à l'item > taux plat propre à l'item > palier général > taux plat général (`quotas.computeVentePay`). Un item sans override retombe sur le palier/taux général, appliqué à la quantité MISE EN COMMUN (`pooled` = total vente moins les items ayant leur propre override) — jamais le palier général appliqué item par item, sinon les tranches ne correspondraient pas au bon total. `SalaryTier.upTo: null` = tranche finale sans limite, au plus une par `(guildId, item)` — vérifié en code dans `handlePalier` (`modules/config.ts`), pas par contrainte DB. Sans tranche finale, la dernière tranche s'applique au-delà de sa borne (jamais 0 $, voir `computeTierPay`) ; `/config palier add`/`list` le signalent. Le `item` d'un taux ou d'un palier doit être un item suivi : `/config salaire`/`palier` le refusent sinon et enregistrent le nom exact configuré (`canonicalItem`), un nom mal orthographié ne correspondant à aucune vente (piège n°1 appliqué à la paie). La répartition entre items à override et reste mis en commun vit dans une seule fonction (`quotas.repartirVente`), partagée par le calcul et l'affichage.
- Le bot est **multi-tenant** (voir section dédiée plus bas) : un seul déploiement sert plusieurs serveurs Discord à la fois, chacun réutilisable pour n'importe quelle organisation RP illégale sans toucher au code, via `/config`.

Avant de "generaliser encore plus" une de ces zones volontairement fixes, vérifier avec l'utilisateur que ça vaut la complexité ajoutée (moteur de formulaire générique, etc.).

## Type d'organisation (`/config type-groupe`)

Chaque guilde peut passer par 4 tiers — **Indépendant / Petite Frappe / Gang / Organisation** (`GroupTier` dans `src/config-store.ts`) — modifiables via `/config type-groupe set`, persisté comme un `Setting` (clé `TYPE_GROUPE_SETTING_KEY`, scopé par `guildId`) et exposé résolu dans `configStore.get(guildId).TYPE_GROUPE`. Le tier lui-même est ce qui change dans le temps ; les barèmes associés à chaque tier restent fixes dans le code (même logique que `ACTIVITY_TYPES_FIXED` : vérifier avec l'utilisateur avant de les rendre configurables).

Deux mécanismes indépendants en dépendent pour les activités, tous deux résolus dans `configStore.reload()` (un troisième pour les items et un quatrième pour les munitions, plus bas) :
- **`BRAQUAGE_LIMITS_BY_TIER`** : limite hebdomadaire de braquage (Fleeca, Armurerie, Bijouterie, Pinebank, Human Labs) par tier. `0` signifie "tier sans accès à cette activité" — bien distinct de `null` (aucune limite du tout, ex. ATM). **Ne jamais tester `if (!cfg.braquageWeeklyLimit)`** pour décider si une activité est limitée : ça confondrait 0 et null. Toujours `== null` (illimité) vs `!= null` (limité, potentiellement à 0).
- **`LABO_TIERS`** : quels labos existent pour quel tier (Indépendant : Salvia + Branche De Cannabis ; Petite Frappe : Héroïne + Spore X ; Gang : Mexicana + Cannabis ; Organisation : Mexicana + Cocaïne). Une clé absente de `LABO_TIERS` pour le tier courant est désactivée.

Les deux mécanismes alimentent `ActivityTypeConfig.enabled` (calculé dans `reload()`, jamais stocké en base) : `false` masque entièrement l'activité — bouton du panneau, slots de braquage, minuterie, bilan hebdomadaire — plutôt que d'afficher "0/0" ou un labo à l'arrêt. Le nombre/barème reste néanmoins en mémoire (`braquageWeeklyLimit` garde sa vraie valeur, y compris 0) : `triggerActivity` dans `quotas.ts` garde un filet de sécurité (`if (!cfg.enabled) ...`) pour un bouton resté affiché sur un panneau pas encore rafraîchi.

Un troisième mécanisme, au niveau des **items** (pas des activités) : `Item.laboLie` (`/config item add labo_associe:<clé labo> role_labo:<produit|materiau>`) marque qu'un item est lié à un labo donné, avec un rôle. `laboLieRole: 'produit'` : c'est LA drogue que ce labo fabrique (ex. "Cocaïne" → `labo_cocaine`) — dans `configStore.reload()`, un tel item est retiré de `VENTE_ITEMS` (donc non déclarable en vente PNJ) et ajouté à `LABO_ITEMS` si et seulement si ce labo fait partie de `LABO_TIERS` pour le tier courant : un tier ne peut pas vendre aux PNJ la drogue qu'il produit lui-même. `laboLieRole: 'materiau'` : une matière première qu'il consomme — ajouté à `MATERIAL_ITEMS` selon la même condition de tier, mais n'affecte jamais `VENTE_ITEMS`/la vente PNJ (sert uniquement à catégoriser l'affichage du stock). Un item sans `laboLie` reste vendable dès que `vente:true`, quel que soit le tier (ex. Ecstasy, Lean), et n'entre jamais dans `LABO_ITEMS`/`MATERIAL_ITEMS`. Ce mécanisme ne modifie ni `Item.vente` en base ni `stockGroup` — seules les listes résolues changent.

Affichage dans le message "Stock Général" (`stocks.ts`, `buildStockEmbed`) : un item avec `laboLie` non nul est **totalement invisible** du corps principal du message, que son labo soit actif pour le tier courant ou non (jamais de repli en item générique) — il apparaît uniquement via l'un des champs dynamiques ci-dessous, recalculés à chaque `reload()` — **💊 Drogues à vendre** : détail par item en stock strictement positif + total (le détail complet, items à 0 compris, reste dans `/drogues-a-vendre`, commande admin gardée en parallèle) ; **🧪 Drogues de production** (rôle `produit`) : détail par item + total ; **🧱 Matériaux de production** (rôle `materiau`) : détail par item, **sans** total — des matières premières hétérogènes n'ont pas de somme qui fasse sens ensemble. Chaque champ n'apparaît que si sa liste est non vide pour ce tier.

La **fabrication/vente de munitions** dépend aussi du tier (`MUNITIONS_FABRICATION_TIER` dans `armurerie.ts`) : Petite Frappe fabrique le pistolet, Gang le SMG, Indépendant et Organisation rien (rangée de boutons masquée). Le stock des deux calibres reste toujours affiché.

`DEFAULT_GROUP_TIER` (tant qu'aucun `/config type-groupe set` n'a jamais été fait) vaut `petite_frappe` — ça correspond aux anciennes valeurs codées en dur (Fleeca/Armurerie 6, Bijouterie/Pinebank 1, Héroïne+Spore X actifs), pour qu'un déploiement existant ne change pas de comportement tant que l'admin n'a pas explicitement choisi un tier.

## Scripts d'investigation & de correction ponctuelle

Pattern établi pour toute opération ad hoc (backfill, vérification de logs, correction manuelle de données) :

1. Écrire un script TS autonome à la racine ou dans `scripts/`, préfixé `_` (ex. `_check-logs.ts`) — jamais dans `src/modules/`.
2. Il importe `./src/db`, `./src/config-store` (avec `await configStore.reload(guildId)` avant tout usage — le bot est multi-tenant, voir plus bas — un script sans guilde précise en tête doit demander/coder en dur celle visée), et si besoin un client Discord (`new Client({...}); await client.login(...)`).
3. Vérifier avec `npx tsc --noEmit`, puis exécuter avec `npx tsx script.ts`.
4. **Toujours supprimer le script après usage** — jamais de résidu dans le repo (déjà exclu par `.gitignore` : `_*.ts`).
5. Pour scanner un salon complet, paginer avec `channel.messages.fetch({ limit: 100, before })`, tant que `batch.size === 100`. Un scan complet peut prendre plusieurs minutes → lancer en tâche de fond plutôt que bloquer.
6. Un message peut contenir plusieurs embeds : toujours `msg.embeds.flatMap/map(e => e.description)`, jamais juste `embeds[0]`.

**Ne jamais modifier des données réelles (stock, taxes, stats…) sans confirmation explicite de l'utilisateur.** Une « analyse » ou un mot comme « ponctuel » signifie lecture seule.

## Rafraîchir un message permanent après une correction manuelle en base

Chaque module avec un message permanent (stock, quotas, armurerie, taxes) expose une fonction de refresh (`updateStockMessage`, `initPermanentMessage`/`updatePermanentMessage`…). Après une correction directe en base via un script `_*.ts`, toujours appeler cette fonction dans un mini-script avec client Discord pour que le message affiché reflète le changement immédiatement.

**Aucun de ces rafraîchissements ne doit dépendre d'un (re)démarrage du bot** — le process n'est pas censé redémarrer une fois lancé en prod. Toute écriture `/config` qui touche un panneau (salon, item, tier…) doit appeler explicitement la fonction de refresh concernée dans son handler, plutôt que compter sur le prochain événement qui la déclencherait indirectement (un mouvement de coffre, une déclaration d'activité…) ou sur le cron horaire de rattrapage des quotas — voir `handleChannel`/`handleTypeGroupe`/`handleItem`/`handleCategory` dans `config.ts` pour le pattern à suivre à chaque nouvelle sous-commande.

À l'inverse, `stocks.updateStockMessage` ne doit **pas** rafraîchir systématiquement l'armurerie sur n'importe quel mouvement de coffre — seulement si l'item déplacé appartient à `MUNITIONS_STOCK_GROUP` (voir le paramètre `skipArmurerie`, utilisé uniquement par `stocks.handleMessage`, le point d'entrée à très haute fréquence). Les autres appelants (resync, correction manuelle, changement de salon/tier — tous rares) gardent le comportement par défaut, plus simple.

## API REST (`src/api/`) — interopérabilité avec un outil externe

Petite API en lecture seule, dans le MÊME process que le bot (pas de second service à déployer), mais **multi-tenant** : une seule instance sert les sites externes de plusieurs guildes à la fois (voir section dédiée plus bas). Désactivée par défaut : n'existe que si `API_PORT` est dans `.env` (voir `startApiServer` dans `src/api/server.ts`, appelée depuis `index.ts` après `clientReady`). Voir le README (section « Interopérabilité » et « Plusieurs guildes ») pour la mise en place et la liste des endpoints.

- **Authentification = connexion Discord (OAuth2), pas de clé API statique.** `src/api/auth.ts` échange le code OAuth contre l'identité Discord de l'utilisateur (scope `identify` seul), puis résout ses rôles via **le client du bot lui-même** (`guild.members.fetch` + `permissions.isAdmin(guildId, member)`) — pas un second aller-retour à l'API Discord pour les permissions. Ça garantit que les règles d'accès sont EXACTEMENT les mêmes qu'en Discord, jamais une logique dupliquée qui pourrait diverger.
- **`/auth/login` exige `?guild=<guildId>`** (validé via `guild-registry.isKnownGuild` avant tout contact Discord) : ce `guildId` est porté par le paramètre `state` OAuth (déjà utilisé comme anti-CSRF, format `${csrf}.${guildId}`) jusqu'à `/auth/callback`. Le résultat (id, username, isAdmin, **guildId**) est signé dans un JWT (`API_JWT_SECRET`, 7 jours) et transmis au site externe en fragment d'URL (`${Guild.frontendUrl}#token=...` — PAS une variable d'env globale, voir `/config site-externe`) — jamais en query string (finirait dans des logs serveur) ni en cookie (le site externe n'est pas censé partager le domaine de cette API).
- Rôle membre (`/config role set membre`, `permissions.hasApiAccess`) : exigé au login et à chaque requête ; non configuré = admins seulement (jamais « tout membre du serveur »), cas signalé par `/config role list`. Ne jamais ajouter de route `/api` qui contourne `requireAuth`.
- Un seul niveau d'accès de base : `requireAuth` (membre de la guilde portée par le JWT, porteur du rôle membre ou admin) sur toutes les routes, y compris `/api/stocks`, `/api/taxes` et `/api/armurerie` (le rôle membre ouvre tout le back-office web). Pas de rôle dédié aux taxes (`TAXES_ROLE_ID` retiré, cible `taxes` effacée par la migration `retire_role_taxes`). **Chaque route de `src/api/routes/*.ts` DOIT filtrer par `req.apiUser.guildId`** — l'oublier fait fuiter les données d'une guilde vers le token d'une autre.
- CORS (`server.ts`) : `origin()` dynamique via `guild-registry.isKnownCorsOrigin` (le site d'AU MOINS une guilde active) plutôt qu'une seule valeur globale — grossier par nature (le JWT n'existe pas encore au moment du preflight), la vraie isolation se fait par requête via `req.apiUser.guildId`.
- **Lecture seule pour l'instant, volontairement.** Écrire depuis l'extérieur (ex. marquer une taxe payée depuis le web) redemanderait la même validation que côté Discord (unicité par groupe ET par type, sauf `vente` sans limite — voir `modules/taxes.ts`) — à construire plus tard si un vrai besoin se présente, pas par anticipation. Si ça change un jour, vérifier avec l'utilisateur avant d'ajouter des routes d'écriture (même logique que pour les autres zones volontairement limitées du projet).
- Chaque route de `src/api/routes/*.ts` réutilise les fonctions `db.ts`/`configStore` existantes plutôt que de recalculer une logique déjà présente dans un module Discord (ex. `armurerie.getMunitionsSummary()`, exportée spécifiquement pour être partagée entre le panneau Discord et la route `/api/armurerie/ammo` ; même principe pour `taxes.getTaxesReferentiel()` (`/api/taxes/types`) et `quotas.getBraquageSummary()` (`/api/quotas/braquages`) — source unique, jamais deux calculs divergents).
- **`stats` (cache "semaine en cours", vidé à chaque reset) vs `transactions` (jamais purgé, juste soft-delete) :** le panneau Discord en direct lit `stats` (rapide). Les endpoints `/api/quotas*`/`/api/ventes*` acceptent un `?week=` (semaine ISO passée, résolue par `src/api/week.ts` en période de paie : du dimanche 19h précédent au dimanche 19h de cette semaine, heure de Paris, pour recouper exactement la paie publiée) — impossible à servir depuis `stats`, qui ne connaît que la période actuelle. Les fonctions `*ForRange` de `modules/quotas.ts` (`getUserQuotaSummaryForRange`, `getAllUserQuotaSummariesForRange`, `getUserPayForRange`, `getAllUserPayForRange`, `getClassementRankingForRange`, `getGroupSummaryForRange`) et `getVenteTotalsForRange`/`getVenteDetailForUser` dans `db.ts` reconstruisent le même calcul depuis `transactions` sur une plage `[since, until)` arbitraire — un seul chemin de calcul pour "semaine en cours" et "semaine passée" côté API (jamais de recours à `stats`), pour ne pas faire diverger deux logiques. Le panneau Discord live, lui, garde son propre chemin `stats` inchangé (`getUserQuotaSummary`, `getSalaryRanking`, etc.) — ne pas les fusionner, la séparation est volontaire (voir commentaire en tête de section dans `quotas.ts`).
  - Une vente confirmée écrit une `transaction` (`action: 'vente'`, `type` = l'item vendu — voir `tryConfirmMoneyDeposit`/`tryConfirmRedeposit` dans `ventes.ts`) exactement comme n'importe quelle activité déclarée : `/api/ventes` (total par joueur) lit donc la MÊME table que `/api/quotas` (catégorie `vente`), jamais `pending_sales` (qui inclut aussi les ventes non confirmées/reposées/expirées — pas ce que "vendu" doit compter).
  - **Piège à ne pas reproduire** : `/config quota` (objectifs), `/config salaire` (taux) et `/config palier` (barème) ne sont PAS historisés, seule la valeur actuelle existe. Une requête `*ForRange` sur une semaine passée applique donc les valeurs ACTUELLES à l'activité de cette semaine-là. Documenté dans le README ; si un jour ça doit être corrigé, il faudra historiser `QuotaTarget`/`SalaryRate`/`SalaryTier` (vérifier avec l'utilisateur avant de s'y lancer, même logique que les autres zones volontairement simplifiées du projet).
- **Noms d'endpoint** : la plupart des groupes de ressources gardent un nom français (`/api/stocks`, `/api/quotas`, `/api/taxes`, `/api/ventes`), sauf `armurerie` dont les sous-routes sont en anglais (`ammo`, `ammo/history`) — décision explicite de l'utilisateur : un groupe d'endpoints ne doit jamais mélanger les deux langues en son sein, mais rien n'impose que tous les groupes utilisent la même langue entre eux. `armurerie` n'a PAS de préfixe `weapons` sur sa ressource principale (`GET /api/armurerie`, `GET /api/armurerie/search`) : le fichier de routes EST déjà `/api/armurerie`, un préfixe supplémentaire serait redondant — seule `ammo` (ressource secondaire distincte) garde le sien.
- **Routes dynamiques (`:id`) toujours à plat, jamais namespacées** (`/api/stocks/:channelId`, `/api/quotas/:userId`, `/api/quotas/pay/:userId` — pas `/api/stocks/coffres/:channelId`) : décision explicite de l'utilisateur, pour cohérence entre tous les groupes de l'API.
- **Ordre des routes dans chaque fichier** : l'endpoint générique (`/`) EN PREMIER, puis les routes statiques plus spécifiques (`/history`, `/search`, `/pay`, `/summary`...), et la route dynamique (`/:id`) TOUJOURS EN DERNIER — sinon Express l'interpréterait comme le paramètre (ex. `/quotas/ranking` matcherait `/:userId` avec `userId="ranking"` si `/:userId` passait avant). Décision explicite de l'utilisateur après avoir repéré `quotas.ts` mal ordonné (`/summary`/`/ranking`/`/pay` avant `/`) — vérifier cet ordre à chaque nouvelle route ajoutée à un groupe existant.
- **`?type=` des taxes** accepte trois formes : un type fixe, le type fictif `zone` qui regroupe TOUTES les zones (`ZONE_TYPE_KEYS`, exportée depuis `modules/taxes.ts`), ou la clé d'une zone précise (`isZoneType()`, aussi exportée) pour cibler une seule — `resolveTypeFilter` dans `src/api/routes/taxes.ts` gère les trois. `db.findTaxes(guildId, { types, expired, query, limit })` (dans `db.ts`) est la fonction générique derrière `/api/taxes` (liste, filtres type/statut) ET `/api/taxes/search` (recherche par nom dans un type).
- **`CoffreStock` (détail par coffre/salon `logs_coffres`) est la SEULE table de stock.** Aucun total global n'est stocké : `db.getAllStocks`/`getStock`/`getStocksByItems` le recalculent à la lecture comme la somme des coffres pour chaque item (`prisma.coffreStock.groupBy`/`aggregate`), limitée aux coffres actuellement suivis (`configStore.coffreChannelIds`, paramètre `channelIds` obligatoire) : un coffre retiré de la config garde ses lignes (il les retrouve s'il est réajouté) mais ne compte plus, figé, dans le total. Un compteur global tenu à part divergerait : chaque table plafonne sa propre valeur à 0 (`GREATEST(quantite + delta, 0)`), donc un retrait absorbé côté coffre ne le serait pas côté total. **Ne jamais introduire de compteur global séparé** : toute nouvelle façon de faire varier le stock doit écrire dans `CoffreStock` uniquement, le total suit automatiquement.

## Multi-tenant — un déploiement, plusieurs guildes

Un seul process/base sert plusieurs serveurs Discord à la fois, données totalement étanches. Chaque fonction/route qui touche une donnée métier prend `guildId` en paramètre explicite, jamais un identifiant de guilde en dur.

- **`Guild` (table + `src/guild-registry.ts`)** : LE registre de "quelles guildes ce déploiement sert" — à ne pas confondre avec `config-store.ts` (config métier d'UNE guilde déjà connue). `registerGuild`/`deactivateGuild` sont appelés depuis les événements `guildCreate`/`guildDelete` (`index.ts`) — `deactivateGuild` est un **soft-delete** (`active:false`), les données métier d'une guilde qui retire le bot ne sont jamais supprimées (elle peut revenir). `frontendUrl`/`corsOrigin` (site externe autorisé pour l'API, voir `/config site-externe`) vivent ici, PAR GUILDE.
- **Toutes les tables métier ont une colonne `guildId`, filtrée par chaque requête** (voir `prisma/schema.prisma`). Pour les tables de configuration et d'état (`Setting`, `Item`, `Stat`, `CoffreStock`, `Cooldown`…), elle fait partie de la clé primaire. Les tables d'événements (`Transaction`, `Braquage`, `Taxe`, `Arme`, `PendingSale`, `StockHistory`, `Fourriere`, `MunitionVente`, `SalaryTier`) ont un `id` autoincrémenté seul comme clé : toute écriture par `id` y passe OBLIGATOIREMENT `{ id, guildId }` (voir `db.ts` ci-dessous) — une nouvelle table sur ce modèle doit suivre la même règle. `Arme.reference` et `Vehicule.plaque` sont uniques `@@unique([guildId, ...])`, pas globalement — une référence d'arme ou une plaque identique peut exister dans deux guildes différentes sans conflit.
- **`src/db.ts`** : chaque fonction exportée prend `guildId` en premier paramètre. Les fonctions identifiées par un `id` autoincrémenté seul (taxes, armes, ventes en attente, transactions) utilisent `updateMany`/`deleteMany({ where: { id, guildId } })` plutôt que `update`/`delete` — un `id` d'une autre guilde n'affecte alors silencieusement aucune ligne, défense en profondeur contre une mutation croisée. Les fonctions de purge/reset globales (`resetStocksForResync`, `performWeeklyReset`, `clearFourrieres`, `cleanOldBraquages`, le plafond 500 lignes de l'historique de stock) DOIVENT filtrer par `guildId` — sans ça, une guilde purge/écrase les données d'une autre.
- **`src/config-store.ts`** : cache `Map<guildId, BotConfig>`, pas une config globale unique. `get(guildId)`/`reload(guildId)`/`mutate(guildId, fn)` — jamais d'argument optionnel. `reloadAll(guildIds)` recharge toutes les guildes actives séquentiellement (une guilde en échec n'empêche pas les autres) — appelé une fois au démarrage.
- **`index.ts`** : l'initialisation d'une guilde est en deux phases — `prepareGuild` (registre, config, items par défaut : de quoi répondre aux interactions) puis `initGuild` (commandes slash, rattrapage des logs, panneaux permanents). Au démarrage, `prepareGuild` passe sur TOUTES les guildes avant le premier `initGuild`, pour que la n-ième guilde ne reste pas inutilisable pendant le rattrapage des précédentes ; l'API et les crons démarrent entre les deux phases. `guildCreate` enchaîne les deux (`setupGuild`). Une guilde dont `prepareGuild` échoue est retentée toutes les 5 minutes par un cron, et chaque étape de `initGuild` est indépendante des autres (`step`). Les commandes slash sont déployées PAR GUILDE (`Routes.applicationGuildCommands(CLIENT_ID, guildId)`), jamais globalement. Tous les crons bouclent sur `forEachActiveGuild()` (séquentiel, jamais `Promise.all` — le bot est sensible au rate-limit Discord par itération), avec un `try/catch` par guilde.
  - **Le traitement temps réel des logs coffres/garages d'une guilde attend la fin de son rattrapage** (`logsCaughtUp` dans `index.ts`) : traité avant, un message ferait avancer le curseur `last_*_msg` au-delà des messages publiés pendant l'arrêt du bot, jamais rejoués ensuite. Un message arrivé pendant le rattrapage est à la fois récupéré par celui-ci et mis en attente : `stocks.handleMessage`/`garages.handleMessage` ignorent tout message dont l'ID n'est pas postérieur au curseur, pour ne pas l'appliquer deux fois. Toute nouvelle source de messages rejouée au démarrage doit suivre ce même couple porte + curseur.
  - **Tout traitement de log d'une guilde passe par sa file (`guild-queue.ts`, `runExclusive`)** : temps réel, rattrapage, `/sync-stock`, expiration des ventes (qui attend en plus la fin du premier rattrapage de la guilde : un dépôt d'argent posté pendant l'arrêt doit pouvoir confirmer sa vente avant qu'elle n'expire). discord.js n'attend pas un handler avant de lancer le suivant ; sans file, deux messages d'une guilde liraient puis écriraient en parallèle le même curseur ou la même vente en attente. Ne jamais appeler `runExclusive` depuis un traitement déjà dans la file de la même guilde (attente infinie).
  - **Un message de coffre s'applique en UNE transaction** (`db.applyStockMessage` : mouvements, historique, curseur) : un arrêt au milieu ne laisse ni message marqué traité sans mouvement, ni message à moitié appliqué. Le curseur n'est écrit qu'APRÈS application (garages compris). Le salon est marqué à rattraper (`needsCatchUp`/`catchUpPending`) dès qu'une lecture d'historique (retentée puis propagée — jamais prise pour "plus de messages", voir `discord-fetch.ts`) OU une écriture échoue : le message temps réel suivant relance alors le rattrapage au lieu d'avancer le curseur par-dessus le trou. Sur une nouvelle session gateway (`shardReady` après le premier), toutes les guildes sont marquées de façon synchrone AVANT le moindre message temps réel, puis leurs rattrapages mis en file ensemble : discord.js ne rejoue pas les événements manqués pendant une coupure.
  - `/sync-stock` (`stocks.fullResync`) : remise à zéro (stock, historique, curseurs à `0`) en une transaction ; les suites (ventes, alertes) des messages publiés PENDANT la resync sont déclenchées par elle, le temps réel les trouvant déjà appliqués ; un salon illisible la fait échouer. Interrompue, la reprise ne redéclenche pas les suites des messages antérieurs à son début (`resyncStartedAt`).
  - Un message rattrapé plus ancien que le démarrage du process ne rejoue que la confirmation de vente par dépôt d'argent (`ventes.onStockEntry(..., { replay: true })`), jamais d'alerte ni de nouvelle vente en attente ; un message postérieur (coupure de connexion) a tous ses effets. Tout ce qui dépend du temps se mesure à l'heure du message de log (`StockEntry.timestamp`), jamais à celle du traitement : fenêtre de confirmation d'une vente, horodatage de sa `Transaction` (semaine de paie), historique de stock.
- **Modules** : chaque fonction exportée prend `guildId` en paramètre explicite, ou le dérive de `interaction.guildId!`/`message.guildId!` en tête de handler (jamais un `configStore.get()` implicite). **Ne jamais utiliser `client.guilds.cache.first()`** pour résoudre "la" guilde d'un appel — toujours `client.guilds.cache.get(guildId)` avec le `guildId` reçu en paramètre ; `.first()` retourne silencieusement la mauvaise guilde dès qu'il y en a ≥2.
- **API (`src/api/`)** : voir section dédiée plus haut — JWT scopé par guilde, login via `?guild=`, CORS par guilde, chaque route filtrée par `req.apiUser.guildId`.
- **Toute nouvelle table** ajoutée au schéma doit avoir `guildId` dans sa clé primaire/unique dès la conception — pas un correctif après coup.

## Discord : limites à connaître

- **25 choix max** sur un `.addChoices()` de slash command → passer en `.setAutocomplete(true)` + handler `interactionCreate` (`isAutocomplete()`) dès que la liste peut dépasser 25 (ex. items, activités).
- **25 options max** sur un `StringSelectMenuBuilder` → pattern « modal de recherche avant select » (armurerie, taxes) : demander un texte de recherche optionnel, filtrer, puis afficher le select avec au plus 25 résultats.
- **5 boutons max par `ActionRow`, 5 rows max par message** → le panneau de quotas (`quotas.ts`, `buildButtonRows`) gère ça dynamiquement : jusqu'à 3 rangées de boutons directs (15 activités), un menu déroulant de repli au-delà (`act_more_select`, 25 de plus), puis la rangée fixe des vues. Si `ACTIVITY_TYPES_FIXED` (config-store.ts) dépasse ces capacités (40 activités avec bouton), les activités en trop n'apparaissent plus dans le panneau — un `console.warn` le signale.
- Un renommage de salon est limité à 2 fois / 10 min / salon (statut labo 🔴/🟢, voir `alertes.ts`).
- Éditer un message (`msg.edit`) remplace entièrement ses `components` — pas besoin de « reconstruire » le message pour qu'un changement de couleur de bouton soit pris en compte.
- **100 caractères max** sur la description d'une commande/sous-commande/option slash (limite distincte de celle des embeds, 256/4096) — un dépassement bloque silencieusement le déploiement de TOUTES les commandes de la guilde (juste une erreur dans les logs). Relancer `npx tsx scripts/check-description-lengths.ts` après tout ajout/modification d'option.

## Robustesse

- **Filets globaux** (`index.ts`) : `client.on('error')` (erreurs WebSocket Discord, discord.js se reconnecte seul) et `process.on('unhandledRejection')` loggent sans tuer le process — une erreur isolée dans un handler ne doit pas couper le bot pour toutes les guildes. Chaque handler d'événement (`messageCreate`, `messageReactionAdd`, `guildCreate`, `guildDelete`, `interactionCreate`) a quand même son propre `try/catch`, et ignore une guilde dont la config n'est pas encore chargée (`configStore.has`). À l'inverse, un échec de l'initialisation globale (`startup()`, base injoignable au démarrage typiquement) fait **exprès** `process.exit(1)` : sans ça, le filet global laisserait un bot connecté mais sans config ni crons, que systemd/Docker ne relanceraient jamais.
- Pattern de reset hebdomadaire auto-réparant : au lieu de compter sur un cron qui tombe pile à l'heure, vérifier à chaque démarrage **et** toutes les 15 min si le reset attendu (dimanche 19h Europe/Paris) est en retard, et le déclencher si oui (`quotas.checkWeeklyReset`). Évite de perdre un reset si le bot était down au moment du cron.
  - **Reset et publication sont découplés.** Le reset est une seule transaction (`db.performWeeklyReset`, sous verrou exclusif de `Stat` — chaque crédit/débit de stat prend le même verrou en partagé) : chaque semaine close l'est pile au dimanche 19h (`paris-time.weeklyBoundariesBetween`, mêmes bornes que `?week=`), une période par dimanche manqué ; `Stat` est reconstruit depuis les `Transaction` postérieures à la dernière frontière ; `last_weekly_reset` passe à cette frontière ; les semaines closes sont AJOUTÉES à `weekly_publication` (liste), jamais une publication en attente écrasée. La publication (bilan, paie, fourrières) est calculée depuis `Transaction` sur chaque période close ; ses trois étapes sont indépendantes (une en échec n'empêche pas les autres) et cochées une fois postées ; `permanent-message.sendOnce` évite de reposter après un arrêt entre l'envoi et la coche. Paie et fourrières sont découpées en plusieurs messages (`buildChunkedEmbeds`, un embed par message : Discord plafonne aussi le total d'un message). L'archive des fourrières ne concerne que celles antérieures à la fin de la semaine close. Ne jamais recalculer la paie publiée depuis `Stat` ni avancer `last_weekly_reset` hors de cette transaction.
  - Une guilde sans `last_weekly_reset` (jamais remise à zéro) l'initialise à maintenant au lieu de déclencher un reset immédiat.
- **Écritures concurrentes** : toute séquence lire-puis-écrire sur une donnée partagée passe par une transaction DB qui revérifie l'état au moment d'écrire — jamais par une vérification faite à l'ouverture d'un modal/menu, qui peut rester ouvert longtemps. Déclarations (`db.recordActivity` : limite de braquage et cooldown sous verrou `pg_advisory_xact_lock`), `/supp` (`db.suppTransaction`), ventes en attente (`db.transitionPendingSale`/`confirmDeclaredSale`/`applyRedeposit`/`applyReposeRedeposit`/`accumulatePendingSale`/`updatePendingSaleQuantite` : transitions conditionnelles au statut attendu, verrou `vente:<id>`, quantités incrémentées jamais réécrites en absolu ; une vente reposée n'est vérifiée que quand tout le retrait est revenu), taxes (`db.addTaxeIfFree`, `renewTaxe` — qui revérifie l'unicité sous le verrou de création quand il réactive une taxe expirée).
- **Une soumission ne fait jamais foi par son `customId`** : `quotas.fluxAutorise` vérifie que le flux (modal simple, modal quantité, labo, braquage) correspond bien à l'activité, et qu'elle a un bouton (`panelButton`) — sinon `modal_act_<braquage>` contournerait la limite, `act_select_<activité à cooldown>` le cooldown, `modal_act_vente` le circuit retrait → dépôt d'argent.
- **Après une déclaration, répondre d'abord, publier ensuite** (`quotas.confirmDeclaration`) : Discord n'attend que 3 s ; un membre qui voit un échec alors que tout est enregistré déclare une seconde fois. Les suites (log, panneau, salon de labo, alerte braquage) sont publiées même si la réponse échoue. Le Stock Général est rafraîchi quelques secondes après une rafale de mouvements, une seule fois (`stocks.schedulePanelRefresh`), et jamais avant les suites d'un mouvement.
- **Arrêt propre** (`index.ts`, `shutdown`) : SIGTERM/SIGINT arrêtent les crons, laissent finir les files de logs (8 s max), puis ferment Discord et la base. `init: true` dans `docker-compose.yml` pour que le signal atteigne le process.
- **Messages permanents** (`permanent-message.ts`, `upsertPanel`, panneau documentation compris) : retrouvés par ID stocké puis par titre d'embed ; seule l'erreur Discord "message inconnu" (10008) vaut suppression — une erreur passagère ne fait jamais recréer un panneau qui existe toujours.
- **Modules partagés, à réutiliser plutôt que recopier** : `serial.ts` (exécution en série par clé — files de logs, panneaux, rappel de quota), `discord-fetch.ts` (lecture d'historique retentée puis propagée, `isMissingAccess` : une boucle d'envoi s'arrête sur une permission manquante plutôt que de multiplier les refus, comptés dans une limite Discord commune à toutes les guildes), `parse.ts` (nombres saisis), `paris-time.ts` (bornes du dimanche 19h).
- **Initialisation d'une guilde** : si l'insertion des items par défaut échoue, la config est retirée du cache (`prepareGuild`) pour que le cron de reprise la retente, au lieu d'une guilde à moitié prête dont les messages de log attendraient sans fin. `configStore.mutate` recharge le cache même quand l'écriture échoue en route.
- Identifier un message applicatif (rappel, message permanent) par le **titre de son embed**, pas seulement par un ID stocké en base — évite une course entre `channel.send()` qui résout et l'écriture en base qui suit.
- **`node-cron` n'a aucune protection contre le chevauchement** (vérifié dans ses sources — pas de mécanisme `concurrency`/`noOverlap`) : il déclenche sur l'horaire, peu importe si l'exécution précédente est terminée. Pour un cron dont le corps peut dépasser son propre intervalle (ex. `alertes.checkExpiredCooldowns`, toutes les minutes, qui boucle sur un envoi Discord + un marquage DB par ligne), un verrou `isRunning` en mémoire (booléen posé en entrée, remis à `false` dans un `finally`) est nécessaire — sinon un 2ᵉ passage redémarre sur des lignes pas encore marquées traitées par le 1ᵉʳ (ex. double notification). Voir `checkExpiredCooldowns` pour le pattern. Les crons à intervalle large (15 min+) dont le corps est court n'en ont pas besoin ; `checkWeeklyReset` en a un, sa publication pouvant attendre Discord longtemps.
- **`Transaction`/`PendingSale`/`MunitionVente` ne sont jamais purgées automatiquement pour `Transaction`, mais le sont pour les deux autres** — distinction volontaire, pas un oubli : `Transaction` alimente la navigation par semaine passée de l'API (`?week=`, voir plus bas), la purger casserait cette fonctionnalité. `PendingSale` (statuts terminaux uniquement — jamais `en_attente`/`declare`, voir `db.deleteOldPendingSales`) et `MunitionVente` (`db.deleteOldMunitionVentes`) sont du pur debris opérationnel une fois leur cycle terminé : purgées après 30 jours par un cron quotidien (`ventes.purgeOldPendingSales`/`armurerie.purgeOldMunitionVentes`, 4h Europe/Paris). Avant d'ajouter une nouvelle table qui grossit sans fin, se poser la même question : sert-elle encore une fois son cycle terminé ?

## Sécurité / secrets

- `.env` (TOKEN, DATABASE_URL) ne doit **jamais** être committé (déjà dans `.gitignore`). Le bot refuse de démarrer avec le mot de passe PostgreSQL d'exemple (`change_me`), un `API_PORT` qui n'est pas un port, ou un `API_BASE_URL` en `http://` hors localhost.
- **`/historique-stock`** exige le rôle membre (ou admin), comme l'API : sur un serveur à invitation publique, être sur le serveur ne suffit pas.
- **Limites de requêtes de l'API** : `apiLimiter` (par IP, avant authentification) est volontairement large, plusieurs sites pouvant partager une IP sortante ; le vrai quota est `guildLimiter`, par guilde.
- **`API_JWT_SECRET` est la seule barrière entre guildes côté API** : un secret devinable permet de forger un JWT avec l'ID Discord (public) d'un vrai admin et n'importe quel `guildId`, que `requireAuth` accepterait (la personne est bien membre). `assertAuthEnv` refuse donc la valeur de `.env.example` et tout secret de moins de 32 caractères — ne pas assouplir ce contrôle.
- `/config` est toujours réservée à la permission Discord native `Administrator`, indépendamment du rôle `ADMIN_ROLE_ID` configurable — évite un problème d'œuf-et-poule sur un serveur fraîchement configuré (voir docstring en tête de `src/modules/config.ts`).
- **Seul un message posté par un bot/webhook, hors réponse à une commande d'application, peut déclencher un mouvement de stock (`stocks.ts`) ou un événement de garage (`garages.ts`)** — règle unique `stocks.isGameLogMessage`, appliquée en temps réel comme au rattrapage et à la resync. La réponse d'une commande d'application est écartée parce qu'un membre peut la déclencher avec sa propre application installée, dont l'auteur est bien "un bot". Un membre ayant la permission d'écrire dans `logs_coffres`/`logs_garages` (mauvaise config des permissions du salon, ou webhook tiers ajouté) pourrait sinon forger un message texte imitant le bot de jeu FiveM et déclencher un vrai mouvement de stock, voire faire créditer une fausse vente (`ventes.tryConfirmMoneyDeposit`). Ce filtre ne dispense pas de restreindre `Send Messages`/`Manage Webhooks`/`Use External Apps`/`Use Application Commands` sur ces salons au bot de jeu uniquement — défense en profondeur, pas un remplacement.
- **Site externe** (`/config site-externe set`) : `https://` obligatoire (sauf `localhost`), pas de `#` — le token y est livré dans l'URL.
- **Items** : `/config item add` refuse un nom qui ne diffère d'un item existant que par la casse (les deux partageraient le même stock et seraient comptés deux fois).
- **Saisies bornées** : quantité déclarée ≤ 100 000 (`MAX_QUANTITE_DECLARATION`), temps de labo ≤ 35 000 min (débordement de `setTimeout` au-delà), jours de taxe 1–365, munitions ≤ 100 000 et prix ≤ 100 000 000, ligne de log de coffre ≤ 1 milliard (colonne `Int`). Un nombre saisi passe par `parse.parseEntier`/`parseMontant`, jamais par `parseInt` seul (`12abc` → 12). Un modal revérifie à la soumission tout ce qui dépend du tier (activité, type de taxe, fabrication de munitions).
- **Texte libre réaffiché** (nom de taxe, arme prêtée, type de produit) : `allowedMentions: { parse: [] }` sur la réponse — un `<@id>` saisi ne doit pinger personne.

## Conventions de code

- Pas de commentaires « ce que fait le code » (les noms suffisent) — seulement le « pourquoi » quand c'est non évident (contrainte Discord, incident passé, choix métier).
- **Jamais de commentaire qui narre une modification** (« avant ça faisait X », « trouvé en audit », « corrigé pour... », « avant on avait... ») — l'historique git/le commit portent déjà cette info, un commentaire relu dans 4 mois ne doit décrire que l'invariant/le risque ACTUEL, jamais l'événement (audit, bug, session) qui l'a introduit.
- Chaque module expose `initPermanentMessage`/`updatePermanentMessage`, `handleButton`, `handleModal`, `handleSelect`, `getCommands()` selon ses besoins ; le routage des `customId` se fait par préfixe dans `src/index.ts`.
- Toutes les fonctions de `src/db.ts` sont **asynchrones** (Prisma), prennent `guildId` en **premier paramètre** (jamais optionnel — voir section Multi-tenant), et acceptent/retournent des nombres pour les timestamps (millisecondes epoch) — la conversion vers/depuis `Date` (colonnes `TIMESTAMPTZ`) se fait uniquement à l'intérieur de `db.ts`, jamais dans les modules métier.
- Toute nouvelle table/fonction de compteur « indicatif » (ex. munitions fabrication/vente) réutilise le pattern : timestamp automatique, somme filtrée par `>= last_weekly_reset` pour un total « cette semaine » qui se remet à zéro tout seul, sans job de reset dédié.
- **Toute modification qui change un comportement visible du bot (nouveau bouton, nouvelle option `/config`, nouveau champ d'embed, nouvelle commande…) impose une mise à jour du manuel** (l'artifact pointé par `MANUEL_URL` dans `src/modules/config.ts`, lié depuis le salon `documentation`) — relire l'artifact (`action: "read"` avec son URL), l'éditer, le republier. Sinon il devient silencieusement obsolète, exactement le même risque que ce README/CLAUDE.md eux-mêmes.

## Checklist avant de livrer une fonctionnalité

Questions à se poser sur tout nouveau handler, cron, commande, route ou table — chacune renvoie à la section qui détaille la règle. Une réponse « oui » sans la protection correspondante est un défaut à corriger avant le commit, pas une amélioration pour plus tard.

1. **Peut-il faire tomber le process ou bloquer les autres guildes ?** `try/catch` propre au handler, `try/catch` par guilde dans un cron, `configStore.has` avant d'agir sur une guilde (voir Robustesse, Multi-tenant).
2. **Peut-il se chevaucher avec lui-même ?** Cron plus court que son pire temps d'exécution → verrou `isRunning` (voir Robustesse).
3. **Écrit-il sur le disque ?** Toute donnée persistante va en base : le conteneur tourne en non-root, `/app` n'est pas inscriptible.
4. **Que se passe-t-il s'il est interrompu ou rejoué ?** Redémarrage au milieu, message arrivé pendant un rattrapage, double clic : l'opération doit être idempotente ou protégée par un curseur/statut revérifié (voir porte `logsCaughtUp` dans Multi-tenant).
5. **Chaque saisie utilisateur est-elle bornée côté serveur ?** Un modal ou une option ne fait jamais foi seul : borner par une donnée réelle en base, et revérifier statut + autorisation AU MOMENT de la soumission, pas seulement à l'ouverture du modal.
6. **Filtre-t-il par `guildId` ?** Toute requête `db.*`, toute route API (`req.apiUser.guildId`), toute nouvelle table (`guildId` dans la clé) — voir Multi-tenant.
7. **Peut-il être déclenché par quelqu'un qui ne devrait pas ?** Message non-bot dans un salon de logs, bouton cliqué par un autre membre, token API d'une autre guilde (voir Sécurité / secrets).
8. **Ouvre-t-il un port ou introduit-il un secret ?** Écoute en loopback par défaut, erreur de `listen` gérée ; secret vérifié au démarrage (présent ET assez solide, pas seulement présent).
9. **Touche-t-il un nom d'item, une limite ou un panneau ?** Nom d'item vérifié dans les vrais logs (piège n°1), `== null` vs `0` pour les limites, refresh explicite du panneau dans le handler `/config`.
10. **Change-t-il quelque chose de visible ?** Manuel, README et ce fichier à jour dans le même commit (voir Conventions de code).

Pour un audit périodique du code existant (par angle, pas en revue généraliste) : commande `/audit [angle]` (`.claude/skills/audit/`), qui lance les prompts de `docs/audits.md` — ce fichier reste la seule source des prompts, la commande n'en contient aucune copie.
